## Подготовить релиз

1. Выбрать проверенный коммит в репозитории https://github.com/daydrneg1974-star/stroy-proekt. Сохранить текущие изменения до переключения; не использовать сброс с удалением работы. Рабочее дерево для воспроизводимого релиза должно быть чистым.
2. Выполнить проверки и сборку (Node.js 22+; для check/build/verify внешние зависимости не требуются):

```sh
git status --short
npm run check
npm run build
npm run verify:release
```

3. Для сохранённого релиза собрать отдельно в новый/пустой каталог, расположенный вне веб-корня. Пример команды: `npm run build -- /absolute/path/to/release-001`, затем `npm run verify:release -- /absolute/path/to/release-001`. На Windows допустим путь `C:\Projects\stroyinzh-releases\release-001`.
4. Зафиксировать вместе с релизом исходный commit, дату, результат проверок и SHA-256 архива. Сохранить `public_html/` и `release-manifest.json` вместе. Не менять готовые файлы: любые правки делаются в исходниках и пересобираются.
5. Обязательно выполнить отдельную браузерную проверку `npm run e2e` (`e2e/contact-release.browser.mjs`). Нужны установленные Playwright и Chromium: модуль задаётся через `STROY_PLAYWRIGHT_MODULE` либо `CODEX_PRIMARY_RUNTIME_NODE_MODULES`, браузер — через `STROY_CHROMIUM_PATH` (по умолчанию `/usr/bin/chromium`). Если инструменты недоступны, проверка должна завершиться ошибкой, не пропуском; выпуск не считать проверенным. Проверяются готовый `public_html` и сценарии [04-user-flows.md](spec/04-user-flows.md): оба режима JavaScript, мобильная ширина, телефон и утверждённые чаты, ручные заметки, копирование/TXT, ошибка буфера, страница данных и отсутствие горизонтального скролла. Локальная проверка не подтверждает работу внешнего аккаунта или доставку.

В сборке 26 файлов: две HTML-страницы, два JS-модуля, 20 медиафайлов, `.htaccess` и `robots.txt`. Единственный allowlist — `scripts/public-files.mjs`. Текст нормализуется до вычисления хешей. `release-manifest.json` содержит размеры и SHA-256 именно готовых файлов, без времени/локальных путей. Он лежит вне `public_html`.

## Обновить сайт

1. Перед заменой сохранить полное текущее содержимое серверного `public_html` в архив **рядом с веб-корнем, не внутри него**. Записать имя копии и действующий исходный commit/релиз в статус. Убедиться, что архив получен и читается.
2. Подготовить рядом новый каталог с **только** содержимым `public_html` нового релиза, включая скрытый `.htaccess`. Проверить имена, размеры и, где позволяет доступ, SHA-256. Не распаковывать весь репозиторий в веб-корень. Манифест, ZIP, отчёты и тесты не должны стать доступными по HTTP.
3. Предпочтительно заменить корневой каталог подготовленным целиком, сохранив предыдущий для отката. Если панель допускает только пофайловое обновление, загрузить сначала медиа и `project.js`, затем `site.js`, `privacy.html` и последним `index.html`; избегать длительного смешения версий. После замены убрать устаревшие публичные файлы только в пределах этого сайта, имея проверенную резервную копию. Не удалять служебные данные сертификата и чужие сайты.
4. Проверить снаружи: HTTPS открывается без предупреждения; HTTP уходит на HTTPS без цикла; `/privacy` и `/privacy/` ведут на `/privacy.html`; все публичные файлы приложения возвращают 200 и совпадают с манифестом. `.htaccess` должен быть недоступен для чтения, но его правила — действовать. Проверить `nosniff`, `no-referrer`, `X-Robots-Tag: noindex, nofollow, noarchive`, robots.txt и noindex в обеих HTML-страницах.
5. Проверить отсутствие выдачи `/README.md`, `/release-manifest.json`, `/.git/config`, архивов и листинга `/assets/`. Убедиться, что браузер загружает хешированные версии обоих модулей. Повторить путь «состав → заметки → копирование/TXT → контакт» и режим без JS на опубликованной странице. Сообщения не отправлять без прямого поручения.
6. Только после внешней проверки обновить [status.md](status.md): опубликованный commit/релиз, сохранённый манифест/архив, резервная копия и доказательства. Проверка кода, HTTP и реального аккаунта — три разных результата. Не помечать чат рабочим только по корректному URL или экрану общего resolver.

`.htaccess` сохраняет ранее проверенное правило для обратного прокси SpaceWeb. Не заменять условие HTTPS универсальным шаблоном без проверки: прежний вариант вызывал цикл редиректов. Локальный HTTP-сервер не проверяет Apache-конфигурацию.

## Откат

При недоступной странице, повреждённых ресурсах или ошибке пути обращения вернуть сохранённый предыдущий `public_html` целиком. Не восстанавливать только один JS/HTML-файл: версии модулей связаны. Проверить HTTPS, главную, privacy, конфигуратор и файлы по манифесту предыдущего релиза; записать фактический откат в статус. Git-историю не переписывать.
